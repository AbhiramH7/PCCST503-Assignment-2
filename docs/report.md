# A Dual-Channel Vector Embedding for Capability Composition

**PCCST503 – Assignment 2.** Formal representations, compatibility and compositional reasoning.
All numbers below are produced by `experiments/run_experiments.py` (full tables in `results/experiment_log.md`, raw data in `results/results.json`).

---

## 1. Problem definition

A formally specified application is $A=(S,C,S_I,G,R,K)$. Each capability is
$C_i=(T_i,I_i,O_i,P_i,E_i,K_i,R_i,Q_i,Rel_i,A_i,M_i)$.
The task is to design $\phi_S,\phi_G,\phi_C$ (or a unified $\phi$) such that vectors preserve the relations needed to

1. tell capabilities apart,
2. relate a capability to the states it can run in,
3. decide *directed* compatibility $C_i\to C_j$ (effects/outputs of $C_i$ satisfy preconditions/inputs of $C_j$),
4. build composites $C_n\circ\dots\circ C_1$ as first-class vectors,
5. relate capabilities to a goal, and
6. handle cost, reliability, availability, risk and resources.

The planner of Assignment 1 is out of scope. No search for action sequences is performed anywhere in this repository; sequences appear only as *test inputs* generated by a reference enumerator (Sec. 8).

**Primary research question.** Can a vector representation of formally specified states, goals and capabilities preserve what is needed for compatibility, composition and goal relevance? **Answer in one sentence:** yes, if the representation is *asymmetric* (separate "requires" and "provides" channels) and *exclusion-aware* (values of one variable share a channel); a single symmetric Word2Vec-style vector could not do it in our experiments (Sec. 9.1: best-case F1 ≈ 0.45 vs 1.00).

## 2. Design requirements

| # | Requirement (from the brief) | Design consequence |
|---|---|---|
| R1 | Identity | Distinct capabilities → distinct vectors (cos < 1 unless indistinguishable in function *and* mechanism) |
| R2 | State awareness | States live in the **same** space as Req/Prov so applicability and "apply" are vector operations |
| R3 | Precondition–effect compatibility ($E_i\Rightarrow P_j$) | Needs **direction**: Prov$_i$ is compared with Req$_j$, not Prov$_i$ with Prov$_j$ |
| R4 | Input–output compatibility | Data items are atoms in the same Req/Prov channels |
| R5 | Similarity ≠ composability | Two different measures on two different blocks (Sec. 5.4) |
| R6 | Composition | Closed operation producing an object of the same type as a capability |
| R7 | Goal relevance | Goals are bundles in the same space; relevance uses *unmet* goal atoms |
| R8 | Operational properties | Kept in a separate profile with explicit combination rules (justified by ablation E5) |
| – | Efficiency | Deterministic hashed codes (no training, no stored embedding table); all-pairs compatibility is one matrix product |

## 3. Related embedding approaches and why they are not enough

| Approach | What it gives | Why it is insufficient here |
|---|---|---|
| **Word2Vec / GloVe** (Mikolov et al., 2013) | Similarity and analogy from co-occurrence | Symmetric; distributional. `CreateOrder` and `CancelOrder` are *close* but are logically opposed; "can follow" is not a co-occurrence statistic. Our baseline in Sec. 9.1 is exactly this kind of symmetric vector. |
| **Knowledge-graph embeddings**: TransE (Bordes et al., 2013), RotatE (Sun et al., 2019) | Relations as translations/rotations; relation paths compose by $r_1+r_2$ or $r_1\odot r_2$ | Compose *relations between entities*, need training triples, no guard/effect semantics, no notion of "requirement already satisfied by an earlier step" so internal links are not cancelled |
| **Order / box embeddings** (Vendrov et al., 2016) | Partial-order entailment $x\preceq y$ | Good for $E\Rightarrow P$ on a single proposition, but no conflict channel and no composition operator |
| **Tensor-product representations** (Smolensky, 1990) | Exact role–filler binding | Dimension grows multiplicatively |
| **Holographic reduced representations / hyperdimensional computing / VSA** (Plate, 1995; Kanerva, 2009) | Fixed-width bundles of hashed codes; set union = vector sum; similarity = overlap size | **Adopted as the base**, extended with an exclusion channel, asymmetric Req/Prov, and a guarded-update composition operator |
| **STRIPS/PDDL semantics** (Fikes & Nilsson, 1971) and **OWL-S IOPE** (Martin et al., 2004) | Exactly the formal model in the brief (preconditions, effects, inputs, outputs) | Symbolic; give the semantics we must preserve, not a vector space. Used here as the *reference semantics* |
| **Compressed sensing / OMP** (Tropp & Gilbert, 2007) | Sparse recovery from few random measurements | Used for the clean-up decoder when the codebook is larger than $d$ |

**Design choice that follows:** adopt VSA bundling for set-valued content, but make it *directional* and *conflict-aware*, and treat composition as an algebra on (Req, Prov) pairs rather than vector addition.

## 4. Proposed representation

### 4.1 Atoms
Every condition is reduced to an **atom** $a=(k,v)$ with *key* $k$ and *value* $v$:

| Source | Atom |
|---|---|
| `x == v` (also effect `x = v`) | $(x,\,v)$ |
| `x > 0`, `x <= 5000`, `x in {A,B}`, `x != v` | $(\text{"x>0"},\ \text{true/false})$ – one *predicate key* per distinct predicate |
| input $(name,type,domain,\text{required})$ / output | $(\text{Data.}name,\ type\,|\,domain)$ |
| resource $r\in R_i$ | $(\text{Resource.}r,\ \text{available})$ |

Atoms with the same key are mutually exclusive. An assignment $x=v$ is **grounded** into $(x,v)$ plus the truth value of every predicate registered on $x$ (e.g. `Cart.item_count = 0` yields $(\text{item\_count}, 0)$ and $(\text{"item\_count>0"},\text{false})$).

Formal entities become atom sets:

$$\mathcal A(S)=\bigcup_{(x,v)\in S}\gamma(x,v)\ \cup\ \{\text{resources available}\},\qquad \mathcal A(G)=\{a(g):g\in G\}$$
$$\mathrm{Req}(C)=\{a(p):p\in P\cup K\}\cup\{\text{required inputs}\}\cup\{\text{resources}\},\qquad \mathrm{Prov}(C)=\gamma(E)\cup O .$$

Global policies in $K$ are attached to a capability as ordinary constraints (`"policies": [...]` in the dataset).

### 4.2 Codes
Each atom has a deterministic code $u_a=[\ell_a\,;\,w_{k(a)}]\in\mathbb R^{2d}$, where $\ell_a,w_k$ are independent Rademacher vectors scaled by $1/\sqrt d$ and seeded by a hash of the atom (no table is stored or trained).

- $\ell_a$ is the **literal** code (unique to key *and* value);
- $w_k$ is the **variable** code, shared by all values of the same key.

### 4.3 Bundles and the two inner-product identities
$\beta(A)=\sum_{a\in A}u_a$. For atom sets $A,B$ with literal / variable halves $\beta_\ell,\beta_w$:

$$\langle\beta_\ell(A),\beta_\ell(B)\rangle\;\approx\;|A\cap B|\ \ (\text{matches}),\qquad
\langle\beta_w(A),\beta_w(B)\rangle-\langle\beta_\ell(A),\beta_\ell(B)\rangle\;\approx\;\#\{k:\ k\in\text{keys}(A)\cap\text{keys}(B),\ \text{values differ}\}\ \ (\text{conflicts}).$$

Noise has standard deviation $\approx\sqrt{|A||B|/d}$. The second identity is what lets the space say *"CreateOrder makes OrderExists = true, CancelCart needs OrderExists = false"* is not merely "no match" but an active **conflict**.

### 4.4 Entities

| Entity | Embedding |
|---|---|
| State | $\phi_S(S)=\beta(\mathcal A(S))\in\mathbb R^{2d}$ |
| Goal | $\phi_G(G)=\beta(\mathcal A(G))\in\mathbb R^{2d}$ (**same space as states**) |
| Capability | $\mathbf r=\beta(\mathrm{Req})$, $\mathbf p=\beta(\mathrm{Prov})$, $\mathbf t=\tau(T)+\tfrac12\sum_{(k,m)\in M}\tau(k{=}m)$, plus a provenance block $\boldsymbol\sigma$ and an operational profile $\mathbf o$ |
| Functional vector | $\phi_C(C)=\big[\,w_R\hat{\mathbf r}\ ;\ w_P\hat{\mathbf p}\ ;\ w_T\hat{\mathbf t}\,\big]\in\mathbb R^{4d+d_t}$, $(w_R,w_P,w_T)=(0.5,1,0.35)$, hats = unit-normalised |

**Decisions on the open questions in the brief**

| Question | Decision | Evidence |
|---|---|---|
| Type/mechanism weight | Small separate block $w_T=0.35$; mechanism tokens inside it | E3: $w_T=0$ makes a resource-identical GUI/EVENT clone cos = 1.0000 (indistinguishable); $w_T\ge1.4$ drops within-function cos to 0.34 (over-separation) |
| Implementation detail in main vector? | Type + mechanism token **in a separate block**, down-weighted | same |
| Resources | Atoms inside Req (so applicability, compatibility and composition handle them uniformly) | E5 resource scenarios |
| Constraints | Predicate atoms inside Req (single-variable predicates) | Sec. 11 limitation |
| Cost, risk, reliability, availability | **Separate profile $\mathbf o$**, combined by explicit rules, *not* inside $\phi_C$ | E5 ablation |
| Unified vs separate $\phi$ | Unified *space* for state/goal/capability atoms; separate *blocks* per role | – |

### 4.5 Operational profile
$\mathbf o=(c_{time},c_{money},c_{res},c_{risk},c_{energy},Rel,A)$, with $A(t)=\mathbb 1[\,open\le t<close\,]$.

$$\text{cost}(C)=\sum_k \lambda_k\,\tilde c_k,\quad \tilde c_k = c_k/\max_{C'}c_k',\quad \lambda=(0.3,0.3,0.1,0.2,0.1);\qquad
\mathrm{quality}(C,t)=Rel\cdot A(t)\cdot e^{-\text{cost}(C)} .$$

## 5. Mathematical formulation

### 5.1 Compatibility (directed)
For $C_i\to C_j$:
$$m_{ij}=\langle\mathbf p_i^\ell,\mathbf r_j^\ell\rangle,\quad
c_{ij}=\langle\mathbf p_i^w,\mathbf r_j^w\rangle-m_{ij},\quad
\delta_{ij}=\frac{m_{ij}}{\|\mathbf r_j^\ell\|^2},\qquad
C_i\to C_j\iff m_{ij}>\tfrac12\ \wedge\ c_{ij}<\tfrac12 .$$
$\delta_{ij}\in[0,1]$ is the *dependency strength* (fraction of $C_j$'s requirements supplied by $C_i$). Because data atoms and state atoms are in the same channel, a link can be due to a precondition/effect match, an input/output match, or both; `explain()` splits the two. The all-pairs matrix is two matrix products, $\mathbf P_\ell\mathbf R_\ell^{\top}$ and $\mathbf P_w\mathbf R_w^{\top}$.

### 5.2 State awareness
$$\text{unmet}(S,C)=\|\mathbf r^\ell\|^2-\langle\phi_S^\ell(S),\mathbf r^\ell\rangle,\qquad C\ \text{applicable in }S\iff\text{unmet}=0 .$$
Because states contain ~45 atoms the raw inner product is noisy at moderate $d$ (σ ≈ √(11·45/d)); the default uses exact clean-up (below), and the raw form is reported in the sweep. Execution is a vector operation:
$$\mathrm{Apply}(S,C)=\beta\big(\{a\in\mathcal A(S):k(a)\notin\mathrm{keys}(\mathrm{Prov}(C))\}\cup\mathrm{Prov}(C)\big).$$

### 5.3 Clean-up memory
$\mathrm{dec}(\mathbf v)$ recovers the atom set of a bundle: exact least squares when $V\le d$ ($V$ = vocabulary size), orthogonal matching pursuit when $V>d$. Composition, `Apply` and exact applicability use it. The codebook is hashed, so only the list of atoms must be kept.

### 5.4 Similarity versus composability
$$\mathrm{sim}(C_i,C_j)=\cos\big(\phi_C(C_i),\phi_C(C_j)\big)\quad\text{(symmetric: "do they do the same kind of thing?")}$$
$$\mathrm{comp}(C_i\to C_j)=(m_{ij},c_{ij})\quad\text{(directed: "can }C_j\text{ run on what }C_i\text{ leaves behind?")}.$$
They are used for different purposes:

* **sim** → *retrieval of substitutes* (alternative implementations are nearest neighbours), clustering, and a sanity check that a composite resembles its parts;
* **comp** → *chaining*; sim is never used to decide chaining.

They are provably independent: sim looks at $\hat{\mathbf p}_i\!\cdot\!\hat{\mathbf p}_j$, comp at $\mathbf p_i\!\cdot\!\mathbf r_j$. Experiments show all four quadrants (Sec. 9.1): similar & not composable (API ↔ DB `CreateOrder`), dissimilar & composable (`CreateOrder→MakePayment`, cos φ = 0.12), similar-ish & *conflicting*, and dissimilar & not composable.

### 5.5 Goal relevance
Let $U=\mathcal A(G)\setminus\mathcal A(S)$ be the unmet goal atoms. Direct contribution:
$$d_i=\max\!\Big(0,\ \frac{\langle\mathbf p_i^\ell,\beta_\ell(U)\rangle-\max(0,h_i)}{|U|}\Big),\quad h_i=\langle\mathbf p_i^w,\mathbf g^w\rangle-\langle\mathbf p_i^\ell,\mathbf g^\ell\rangle\ \ (\text{clobbers a goal variable}).$$
Dependency links on **residual** requirements (those not already true in $S$), zeroed if $C_i$ clobbers any requirement of $C_j$:
$$D_{ij}=\frac{\langle\mathbf p_i^\ell,\beta_\ell(\mathrm{Req}_j\setminus\mathcal A(S))\rangle}{|\mathrm{Req}_j\setminus\mathcal A(S)|}.$$
Relevance is the fixed point of $\ \rho_i=\max\big(d_i,\ \gamma\max_j D_{ij}\rho_j\big)$, $\gamma=0.7$. It marks a capability relevant if it supplies something that is *still missing*, either for the goal or for a relevant capability, and gives 0 to capabilities whose contribution is already satisfied, harmless-but-unrelated, or harmful. This is a relevance score, not a plan: nothing is ordered or searched.

## 6. Capability composition model

For $C_1$ then $C_2$ (written $C_2\circ C_1$), with $\mathrm R_i=\mathrm{Req}(C_i)$, $\mathrm P_i=\mathrm{Prov}(C_i)$ as atom sets (obtained by clean-up from the vectors):

$$\mathrm{Req}(C_2\!\circ\!C_1)=\mathrm R_1\ \cup\ (\mathrm R_2\setminus \mathrm P_1),\qquad
\mathrm{Prov}(C_2\!\circ\!C_1)=\mathrm P_2\ \cup\ \{a\in \mathrm P_1:\ k(a)\notin\mathrm{keys}(\mathrm P_2)\}.$$

The composite's vectors are $\beta$ of these sets, so **a composite is an object of exactly the same type as an atomic capability** (closure) and can be compared, composed, applied and ranked with the same operations.

**Validity.** Composition is *undefined* (raises `IncompatibleComposition`) if some $a\in\mathrm R_2$ has $k(a)\in\mathrm{keys}(\mathrm P_1)$ with a different value, or if a residual requirement contradicts $\mathrm R_1$. A chain is additionally *connected* if each step consumes at least one atom produced so far (`require_link=True`, the default; this matches the brief's definition).

**Other components of the composite**

| Component | Rule |
|---|---|
| type block | $\mathbf t=\mathbf t_1+\mathbf t_2$ (bag of types/mechanisms) |
| provenance block | $\boldsymbol\sigma=\boldsymbol\sigma_1+\rho^{|C_1|}\boldsymbol\sigma_2$, $\rho$ = cyclic shift, atomic $\boldsymbol\sigma$ = hashed id. Slot $k$ is read back with $\rho^{-k}$ and nearest id → ordered **decomposition** |
| time, money, resource, energy | sum |
| risk | $1-\prod(1-r_i)$ |
| reliability | $\prod Rel_i$ (independent failures) |
| availability | intersection of windows |

**Properties.** (i) *Closure*, (ii) *associativity*, $(C_3\circ C_2)\circ C_1=C_3\circ(C_2\circ C_1)$: Req/Prov are a guard + a partial assignment, and composing such pairs is composing partial functions on states, hence associative; type, $\sigma$ (positions are absolute offsets), and the cost rules are associative by construction. Tested empirically (Sec. 9.2): 100 % over all length-3 chains. (iii) *Identity*: the empty capability. (iv) **Not commutative**, as required.
Why not "mean of vectors"? Averaging keeps requirements that were satisfied internally (Sec. 9.2: Req F1 0.72–0.91 for a naive sum vs 1.00).

## 8. Experimental methodology

**Datasets (Deliverable 3).** Three hand-specified problems with initial state, goal, constraints, global policy, resources and operational attributes:

| Domain | Capabilities | Types covered | Contains |
|---|---|---|---|
| `ecommerce` | 12 | API, DATABASE, GUI, EVENT, FUNCTION, FILE, COMPUTATION | the brief's example; 3 implementations of `CreateOrder`; harmful (`CancelOrder`), redundant (`AuthenticateUser`), irrelevant caps |
| `travel` | 11 | API, GUI, MESSAGE, FUNCTION | 7-step dependency structure with data hand-offs; irrelevant + harmful caps |
| `pipeline` | 10 | FILE, COMPUTATION, API, MESSAGE, DATABASE | alternative `TrainModel` (GPU vs CPU); harmful `DeleteDataset` |

**Ground truth.** `reference.py` implements the same atom semantics with Python sets (no vectors). It is *not* an independent specification of the domain, so agreement measures **fidelity of the vector realisation** (noise, clean-up, algebra), not discovery of the semantics. The informative comparisons are against the baselines below.

**Baselines.** (B1) one symmetric bag-of-atoms vector per capability (a Word2Vec-style "all content in one vector"), with the *best possible* cosine threshold chosen with oracle access; (B2) cosine between a capability's Prov vector and the goal; (B3) naive additive composition (union of all requirements).

**Protocol.** 10 codebook seeds per domain; chains of length 2–4 enumerated by the reference (test-set generator only); invalid pairs = all ordered pairs the reference rejects.

### 9.6 Consistency, noise and efficiency

**Consistency across problems:** every metric above is reported for three domains with 10 seeds; F1/AUC are identical across domains and seeds at the default dimension (sd = 0.000), i.e. the representation behaves the same on different vocabularies without retuning.

## 10. Analysis

**Why a single symmetric vector fails (B1).** Compatibility is a *relation between the output side of one capability and the input side of another*. A symmetric bag-of-atoms vector merges both sides, so `CreateOrder`, `CancelOrder` and `CancelCart`, which all talk about orders and carts, sit together; no threshold separates "can follow" from "talks about the same thing" (best oracle-threshold F1 0.44–0.50). Splitting Req/Prov removes the ambiguity; adding a variable channel converts "no match" into "conflict".

**Why composition is not vector addition.** Composition is a *guarded update*, not a union: requirements already produced internally must disappear, effects overwritten later must be replaced. A plain sum retains internal links (Req F1 0.72–0.91 vs 1.00). We therefore operate on the (Req, Prov) channels with clean-up, and keep sequence information in a separate shift-bound provenance block so that order does not contaminate the functional vectors.

**Is it still a "vector embedding"?** Compatibility, applicability, similarity, goal relevance and ranking are direct linear algebra on the vectors (inner products, one GEMM). Composition and `Apply` need a clean-up step (sparse decoding against the hashed codebook), the standard operation in hyperdimensional computing. We regard this as a deliberate trade-off: it makes composition exact and associative at the price of needing the atom list.

**What the experiments do and do not show.** Perfect F1/AUC against the reference mostly shows that the *vector realisation is faithful* when $d$ is large enough (the sweep quantifies when it is not). The scientifically informative results are: (i) the 2× gap to the symmetric baseline, (ii) the four-quadrant similarity/composability table, (iii) the $w_T$ and $w_{ops}$ ablations that justify the block structure, (iv) relevance AUC 1.0 vs 0.66–0.73 for goal cosine, and (v) associativity, rejection and order recovery over 224 reference chains.

**Design trade-offs.**

| Choice | Benefit | Cost |
|---|---|---|
| Hashed codes, no training | deterministic, cheap, no data needed, perfectly reproducible | no *semantic* generalisation: `Order.exists` and `Order.created` are unrelated |
| Exclusion channel | conflicts are explicit | only same-key conflicts are seen |
| Operational data separate | similarity stays functional; availability is time-dependent | compatibility and ranking are two steps |
| Clean-up in composition | exact, associative | needs $d\gtrsim V$ (or sparse recovery) |

## 11. Limitations

1. **Expressiveness.** Conditions are conjunctions of single-variable atoms (plus `in`). No disjunction between atoms, no cross-variable arithmetic (`quantity <= inventory_available`), no quantifiers, no increments (`count += 1`). Constraints such as `x == 5` and `x > 10` live under different keys, so this *requirement-side* contradiction is not detected (effect-side grounding does handle value → predicate).
2. **Exact-match semantics.** Matching is on atom identity. Renamed variables or synonyms are not related; a learned or text-based key encoder could be added to $w_k$ but was not attempted.
3. **Scale.** Clean-up needs $d\gtrsim V$ (or sparse recovery $d\sim k\log V$); for $V\sim10^5$ a hierarchical codebook or an index would be required. The default $d=2048$ is conservative for $V\le40$. All-pairs compatibility is quadratic.
4. **Evaluation.** The datasets are small, hand-written by the same author as the reference semantics, so near-perfect scores are optimistic. No real service catalogue was used. Relevance ground truth is regression-based, not human-labelled.
5. **Relevance** is a max-product fixed point over embedding-derived links, i.e. graph propagation. It is not a planner (no sequence is returned) but it is not purely geometric either.
6. **Operational model.** Independent failures ($\prod Rel_i$), additive costs, window-intersection availability, and hand-set cost weights $\lambda$; real systems have correlated failures and retries.
7. **Provenance block** has capacity $\sim d_s$ and its decoding degrades with chain length ($1/\sqrt n$ signal per slot); tested to length 4.
8. **Hyper-parameters** $(w_R,w_P,w_T)$ were set by ablation on the datasets above, not cross-validated.

## 12. Conclusion

A suitably designed vector representation can capture the structure of a formally specified application, provided the space is **directional** (separate requires/provides channels), **exclusion-aware** (a shared variable channel), and **algebraic** (composition as a guarded update on those channels, closed and associative). Such a representation separates compatibility from similarity (the most similar pair is not composable; the most composable pair is dissimilar), models state and goals in the same space, builds composites that behave like capabilities (including ordered provenance and aggregated operational profile), and ranks goal relevance far better than a goal-similarity baseline (AUC 1.00 vs 0.66–0.73). Operational properties are best kept in a separate profile that gates and ranks compatible candidates. The approach is cheap (≈ 5 µs per pair, 35 MB per 1 000 capabilities) but limited to exact-match, conjunctive semantics and a codebook-sized dimension; learning semantic key embeddings and richer constraint languages are the natural next steps toward the architecture *formal specification → capability embedding → planning → executable application*.
